## 2. 本轮已经完成的分销范围

本轮只实现 D1 第一阶段后端闭环，不改变商城架构和外观：

1. 平台创建分销商。
2. 平台把租户挂载到分销商，移动技术租户组织节点并原子重建闭包。
3. 平台查看分销商列表。
4. 分销商读取 overview、租户聚合列表和单租户聚合。
5. 本月 GMV 口径：Asia/Shanghai 当月已付款订单实付，减去这些订单的成功退款。
6. 佣金尚未建设，返回 `notProvisioned`，不伪装成 0。
7. 写操作要求平台范围、权限、近期 step-up、幂等键、请求哈希和审计。
8. 聚合响应不得返回会员、手机号、地址、收货人或订单明细。

## 5. 必须保留的事实更正

### 5.1 `distributor` 不是 reserved

早期迁移曾抛出 `MEMBERSHIP_SCOPE_KIND_RESERVED`，但函数之后被多次覆盖。

最终生效的 `20260813040000_platform_owner_scope.sql`：

- `validate_membership_scope()` 明确支持 `scope_kind='distributor'`；
- 使用 `org_unit_closure` 验证该分销商是否是 membership 所属租户的祖先；
- 不存在 distributor 的 RESERVED 分支。

不得新增“解锁 distributor”的迁移，也不得修改已应用旧迁移。

### 5.2 分销商自助入口不是死代码

Claude Code 第一轮曾判断“没有地方创建 distributor membership scope，所以自助入口不可达”。这个判断不完整。

当前通用权限链已经支持人工开通：

1. `api_permission_command_center()` 的 `scopeOptions.distributor` 返回 Owner 可授予的分销商节点；
2. `permissionAdminRoutes.ts` 接受 `distributor` scope kind；
3. `api_update_membership_access()` 通过 `api_actor_can_grant_scope()` 校验后写入 `membership_scopes`；
4. `MemberAccessEditor.tsx` 按 `scopeOptions` 通用渲染“分销商”选项并保存；
5. `membershipContext.ts` 从恰好一条服务端 distributor binding 投影 `authorization.distributorId`；
6. 分销商还必须拥有包含 `distributor.read` 的角色，显式 deny 仍然优先。

准确状态：

- 已存在通用权限台人工开通路径；
- 没有专用开户注册向导；
- 尚缺一个“真实分销商 membership 经通用权限台授予后登录并访问 overview”的端到端测试。

## 6. Claude Code 第一轮有效发现

第一轮审查没有发现 P0/P1 漏洞，确认了服务端身份投影、双层权限校验、幂等和隐私聚合方向正确。

需要继续复核的有效问题：

1. `distributorRoutes.ts` 直接 `.find()` platform scope binding，功能当前正确，但应考虑在 `auth.ts` 增加统一的“取服务端 scope binding”辅助函数，避免绕开集中式授权架构门禁。
2. `distributorModel.ts` 的名称、原因和 JSON 元数据只做类型与长度校验，未统一过滤控制字符；在未来管理台展示前应补齐。
3. 租户挂载触发既有 `rebuild_org_unit_closure()` 全表重算；当前正确但存在规模化写放大，需要容量测试，不能直接判为当前功能 bug。
4. `api_platform_create_distributor()` 取得平台组织节点后可增加显式 `not found` 防御守卫，并确保查询条件与前置平台校验完全一致。
