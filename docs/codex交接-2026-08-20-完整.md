# 第一部分 · 前因：为什么会有「抢救」这件事

## 1.1 根本原因是 Git 坏了，而不是有人写错了代码

仓库根目录的 `.git` 曾长期是一个**指向已被删除的父仓库的断裂指针**。后果是连锁的：

1. 无法 `merge`、无法 `diff`、无法 `revert`、无法看历史；
2. 于是「合并分支」变成了**复制目录**——把另一份代码整个盖过来；
3. 目录复制会**静默丢代码**：目标目录里有、来源目录里没有的文件，会在覆盖后消失，而且没有任何提示；
4. 与此同时 CI 长期是红的，没有任何门禁能拦住这种漂移。

工作树里一度存在 **16 份完整的仓库副本**，都在 `pre-contract-code-merge-20260820/` 下面。

## 1.2 实测的损失

用导出符号做差集，对比出的退化：

- **28 个文件退化**
- **64 个导出符号消失**
- **约 1816 行代码丢失**

典型样本：

| 文件                                            | 退化         | 丢了什么                                                                            |
| ----------------------------------------------- | ------------ | ----------------------------------------------------------------------------------- |
| `services/commerce-api/src/api/publicRoutes.ts` | 495 → 253 行 | 大量公共路由                                                                        |
| `apps/auth-web/src/services/auth.ts`            | 586 → 468 行 | `registerMember` / `registerUsernameMember` / `requestRegistrationOtp` 整套注册函数 |

**这句话必须记住**：「红的门禁是负资产——它消耗信任，不提供信号。」

## 1.3 战略反转：不修复退化的树，而是把新东西合到干净基线上

原本的打算是修工作树。实测之后改成了相反的做法：

> 找到一个**未被污染的基线** `77b0500`，把当前树里**只有它有**的新工作，逐项挑到基线之上。

`77b0500` 现在保留为分支 `order/official-port`，**不要动它**。它是判断「某个东西是本来就有、还是我写的」的唯一裁判。

**由此产生的铁律：**

> 看到任何「缺失 / 重复 / 架构不对」的现象，**第一反应是 `git show 77b0500:<文件>` 查基线**，不是动手重写。

## 3.6 输入原语合并与一个真实缺陷

`voucherInput.ts` 曾自带 `isRecord` / `requiredString` / `optionalString`，与 `inputPrimitives.ts` 近似但不等价。合并时实测确认旧语义下：

```
parseIssueInput([])                    ->  {"cardPoolId": null}
parseIssueInput({cardPoolId: ""})      ->  {"cardPoolId": null}
```

即：**一个 JSON 空数组请求体，会被当成合法的「发放电子券批次」请求。**

两条语义决定（已写进模块文档）：

- `isRecord` 取**排除数组**的版本——数组不是 record；
- 可选字段的空串取 **reject**（返回 `undefined` → 422）——「可省略」不等于「可留空」，发钱路径上这种歧义应该报错而不是静默记成「未提供」。前端本来就把空值规范化成 `null`，对现有 UI 零影响。

# 第六部分 · 仍然存在的 P0（一个都没修）

**这些不是代码风格问题，是会让钱和货对不上的缺陷。全部当日实测确认，带证据位置。**

## 6.1 库存只占不放（最严重）

`database/supabase/migrations/20260724070000_production_mvp.sql:560`

全仓 **70 个迁移**里，`inventory` 的数量字段**只有这一处变更**：

```sql
reserved_qty = reserved_qty + (v_item->>'quantity')::integer
```

没有任何一处减少 `reserved_qty`，也没有任何一处改动 `available_qty`。因此：

- 下单即永久占用库存，取消/超时**从不释放**；
- 支付成功**不扣减** `available_qty`，卖出去的货在账上还在；
- 库存数字在任何一次下单流程之后即失去意义。

## 6.2 Outbox 无消费者

- `20260814130000_wechat_order_payment_compliance.sql:934` 定义 `api_claim_wechat_payment_outbox`（`for update skip locked`、worker 租约、2 分钟超时重投）

支付成功时（同文件 `:686`）只更新 `public.orders` 的 `paid_cents` 与 `status`，其余通过 `order.payment_succeeded` 主题投递。该事件无人消费，所以履约、结算、通知、子订单状态**全部停在原地**。

# 第七部分 · 工程约束与验证

## 7.1 编码约束（用户明确要求，全程适用）

- DDD 分层：`domain`（零 IO）→ `application` → `interface`；`infrastructure` 实现 `port`。跨模块只经 port 或领域事件。
- SOLID、迪米特法则；**一个文件一个主要公共概念，超 299 行必须先按职责拆分**（`npm run check:lines` 是硬门禁，不要靠加豁免绕过）。
- 命名：目录单数小写英文；类/组件 PascalCase；函数/变量 camelCase；常量 UPPERCASE。**除 cli、代码审计、配置文件、SQL 迁移和测试外，自有文件与目录名不得出现下划线、连字符、空格或无意义缩写。** `V1` 这类版本后缀已全部清理，不要再引入。
- **金额一律整数分，禁止浮点。**
- 禁止重复逻辑与重复配置；禁止调用点断裂。
- 彻底移除演示态与兼容层，**不保留转发别名**——要么改完所有调用点并删除旧模块，要么不动。
- 数据库改动一律走新迁移文件，**不得修改已应用的迁移**。
- 所有写路径必须要求 `Idempotency-Key` 并落幂等记录；高风险操作要求服务端会话绑定的二次认证。
