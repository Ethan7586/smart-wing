# Google AI Studio Apps：智慧翼移动端生成提示词

目标入口：[Google AI Studio Apps](https://aistudio.google.com/apps)

Google AI Studio 的 Android 平台会生成 Kotlin + Jetpack Compose 原生工程；微信小程序不是其原生平台目标，因此采用 Taro + React + TypeScript，在 Web 平台生成并用 H5 预览，导出后再使用微信开发者工具构建和验收。

## 使用顺序

### Android

1. 在 AI Studio Apps 新建项目，平台选择 `Android`。
2. 上传智慧翼 `brand-mark.svg`、`brand-lockup-horizontal.svg` 和七张界面参考图。
3. 粘贴“提示词 A”。
4. 首轮生成后再粘贴“提示词 C”进行检查和收口。

### 微信小程序

1. 在 AI Studio Apps 新建另一个项目，平台选择 `Web`。
2. 上传同一组品牌资产和参考图。
3. 粘贴“提示词 B”。
4. 在 AI Studio 用 Taro H5 模式预览；下载工程后用微信开发者工具编译 `weapp` 目标。
5. 首轮生成后再粘贴“提示词 C”。

不要把 Android 和微信小程序塞进同一个 AI Studio 项目。两个项目共享相同业务模型、令牌和接口契约即可。

## 提示词 A：Android 原生 App

```text
你是一名资深中国企业福利电商产品设计师和 Android 工程师。请生成一个可运行、可交互、可在浏览器模拟器预览的原生 Android App，产品名为“智慧翼企业福利商城”，英文品牌写法固定为“Smart Wing”。这是 B2B2C 员工福利商城，不是普通餐饮点单 App，也不是任何一家商超的复制品。

技术要求：
- Kotlin + Jetpack Compose + Material 3，单 Activity、单 Module。
- 使用 Navigation Compose、ViewModel、StateFlow、Repository 和清晰的数据类；UI、领域模型、数据访问分层。
- 支持手机和小平板，自适应 360×800、412×915 等常见尺寸，edge-to-edge，正确处理状态栏、导航栏、刘海和字体缩放。
- 所有字符串进入 strings.xml，中文为默认语言；金额使用 Decimal/BigDecimal 思路，禁止 Float 直接计算。
- 默认运行 MockSmartWingRepository，不调用任何真实生产接口，不包含真实密钥、微信支付密钥或合作商超密钥。
- 定义 SmartWingApi 接口和 Mock/Remote 两个 Repository 入口，Remote 仅保留 HTTPS 协议模型和 BASE_URL 配置槽，不执行真实交易。
- 每个核心页面必须有 loading、content、empty、error、offline 状态；使用 skeleton，禁止整页白屏等待。

品牌与视觉：
- 严格使用智慧翼主 VI：主色 #1F5EFF，深色 #143A8F，墨蓝 #07182F，浅品牌蓝 #EAF1FF，背景 #F5F7FA，正文 #172033，次级文字 #64748B，成功 #0F9F6E，警示 #F59E0B，危险 #DC2626。
- 主品牌渐变为 135 度 #1F5EFF 到 #143A8F。
- 字体采用 Android 系统中文字体与 Noto Sans SC fallback；8dp 栅格；页面边距 16dp；触控目标至少 48dp；普通卡片 16dp 圆角。
- 视觉感觉：可信、清晰、企业级但不沉闷，兼顾大型零售 App 的高效率与员工福利的温度。以蓝白为主，商品图片负责丰富色彩。
- 不采用参考图中的土金配色、书法字体或巨大悬浮头像导航。
- 底部固定五栏：首页、分类、购物车、订单、我的。使用标准 Material 3 NavigationBar；购物车数量大于 0 时显示角标。
- 使用上传的智慧翼 Logo 资产。若素材读取失败，用“W 翼形”本地矢量占位，不允许出现破图。

联合品牌规则：
- 智慧翼永远是主品牌；企业/当前福利商城是第二层；麦德龙、沃尔玛、山姆会员商店、大润发、永辉只是合作渠道、门店或履约来源。
- 原型只显示这些名称的文字标签与中性图形占位，不生成或仿制其商标 Logo，不使用其专属品牌色统治页面。
- 所有合作信息标注“演示数据”；为 future brandAuthorization 状态预留字段。
- 客户端永远不直连合作商超。商品、库存、价格、订单、发货、退款都通过 SmartWingApi，由智慧翼服务端聚合。

核心用户：
- 员工“测试买家001”，所属“示范企业 · 数字化推进部”，当前城市“武汉”，当前商城“智慧翼员工福利商城”。
- 福利卡余额 3280.00 元，餐卡余额 850.50 元，优惠券 4 张，积分 1260。
- 手机状态提供两套 fixture：VERIFIED 和 UNVERIFIED。UNVERIFIED 可以浏览、收藏、加购物车，但在提交支付前被明确拦截，并引导“完成手机认证”；不要使用假短信验证码。

合作商超与履约模型：
- 演示渠道：全部、麦德龙、沃尔玛、山姆会员商店、大润发、永辉。
- 数据模型至少包含 PartnerRetailer、RetailStore、Supplier、Product、Sku、StockSnapshot、PriceQuote、FulfillmentOption、EligibilityDecision、CartGroup、Order、PaymentAllocation。
- 每个商品显示来源商超、供货/履约方、门店、库存更新时间、配送方式、预计送达和售后责任方。
- 山姆等渠道的“渠道会员资格”与“智慧翼会员身份”必须分开建模和显示；不能假设互通。
- 支持即时配送、普通快递、到店自提三种履约方式；购物车按来源/履约方分组，并提示将拆成多个子订单。

请生成并连通以下页面与交互：
1. 账号密码登录：账号密码为主；手机、微信与企业微信绑定仅显示“待接入”；登录后进入首页。
2. 首页：企业与城市切换、搜索、扫码入口、福利资产摘要、蓝色活动主视觉、合作商超横向入口、城市专区、企业专享、员工特惠、最近购买和推荐商品。
3. 合作商超中心：按距离、配送时效、营业状态筛选；展示附近门店；门店详情含营业时间、配送范围和同步状态。
4. 分类/搜索：左侧分类或顶部横向分类，自适应屏幕；商品卡展示图片、标题、规格、福利价、市场参考价、来源、库存、资格标签和加入购物车按钮。
5. 商品详情：轮播图、来源与履约、价格、规格、库存、资格原因、剩余限购额度、适用城市、配送预计、售后责任方；服务端最终校验提示。
6. 购物车：按合作渠道/供应商分组；支持勾选、数量、失效商品、价格变化、库存变化和资格变化；底部结算条。
7. 结算：地址/自提点、配送、发票、备注、福利卡/餐卡/优惠券/积分/微信支付组合方案；先展示服务端结算预览；未认证手机时禁用最终支付并解释原因。
8. 支付结果：成功、处理中、失败三态；真实微信支付仅保留 PaymentProvider 接口与“待渠道联调”说明，不模拟真实成功回调。
9. 订单列表：全部、待付款、待发货/备货、待收货、已完成、售后；提供空状态、状态角标、再来一单。
10. 订单详情：主订单和按渠道拆分的子订单、履约时间线、支付分摊、资格快照、售后入口。
11. 动态会员码：条形码和二维码仅用短时 mock token 生成，带倒计时、自动刷新和“请勿截图分享”；显示当前企业、等级、福利余额和适用门店。
12. 资产中心：福利卡、餐卡、优惠券、积分、账单流水；明确不同资产的适用范围。
13. 我的：头像、姓名、企业/部门、手机认证状态、订单入口、收藏、地址、发票、账号安全、设备与退出登录。
14. 城市专区与资格说明：显示“为什么我能看/不能买”、适用城市、员工标签、福利计划和限售剩余额度。

设计参考只借鉴上传截图的结构理念：沉浸式活动主图、会员资产摘要、门店选择、分类商品流、会员码、订单标签、个人中心和空状态。不要复制参考品牌名称、素材、文案、颜色或中央头像导航。

原型数据：
- 至少 24 个演示 SKU，覆盖食品饮料、生鲜、家清、数码办公、家居日用、员工权益卡；平均分布到五个演示合作渠道。
- 至少 5 家武汉演示门店、6 个订单状态样例、3 个不可买原因、2 个库存变化、1 个合作接口降级状态。
- 商品图使用本地可替换占位资源或稳定生成的抽象商品图，不依赖会失效的外链。

验收标准：
- App 首次生成即可编译运行；不留空白页面、未实现点击或破图。
- 所有底部导航、页面返回、搜索、筛选、加入购物车、结算、订单详情、会员码刷新、手机未认证拦截均可在 Mock 模式真实操作。
- 页面信息密度接近成熟大型零售 App，但层级清楚、文字不截断、对比度达 WCAG AA。
- 不声称任何合作商超、短信或微信支付已经完成真实接入。
- 最后在 README 中列出架构、运行方式、Mock/Remote 切换点、仍需真实联调的接口清单和品牌授权注意事项。

请直接生成完整工程，不要只给图片或一页静态首页，也不要先向我提问；对未指定细节做合理且可替换的实现。
```

## 导出后再接真实系统

AI Studio 产物先用于移动端视觉与交互原型。接入当前智慧翼系统时，移动客户端只连接现有智慧翼 BFF；合作商超、短信与微信支付的密钥、签名、回调、幂等、对账和审计均留在服务端。Android 的原生项目与微信小程序工程分别验收，不把一个端的会话、支付或导航实现直接复制到另一端。
