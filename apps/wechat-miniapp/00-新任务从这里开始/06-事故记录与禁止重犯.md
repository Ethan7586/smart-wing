# 事故记录与禁止重犯

## 发生过什么

此前的小程序实现没有严格依据已批准的 VI 和整套设计板，而是把设计稿当作灵感重新绘制。结果虽然具备页面结构，但与目标设计在品牌、布局、图标、素材、比例和安全区上出现明显差距。

主要问题包括：

1. 未先完整阅读 VI、移动设计规范和全部设计板。
2. 将批准设计改成新的卡片系统、阴影、圆角和英文副标题。
3. 使用硬编码颜色和尺寸，没有从设计令牌接线。
4. 使用 emoji、CSS 拼图、临时 PNG、假二维码或临时商品图替代正式资产。
5. 顶部安全区、微信胶囊和刘海位置写死，造成遮挡。
6. “翼码/会员码”发生用户界面命名漂移。
7. 在错误结构上持续局部修补，越修越偏，没有停下来重新对照母版。
8. 曾出现 WXSS 不支持的写法，导致编译失败和白屏。

## 为什么 Ethan 要求删除

删除不是因为缺少功能，而是因为错误实现已经变成错误基线。继续在错误基线上打补丁会：

- 让后续页面复制错误组件和错误视觉。
- 让设计验收越来越困难。
- 消耗更多时间，却无法还原批准的整体比例和秩序。
- 混淆“正式 VI”和“临时代码”的优先级。

因此，Ethan 要求清除当时的丑陋版本，保留正式设计稿、VI、令牌、SVG 和项目配置，再以批准设计为母版重新开发。

## 当前进入新任务时的处理原则

当前 `miniprogram` 可能已经重新出现代码。新任务不得假定它正确，也不得假定它应该删除。必须先只读审查并与设计稿对照；是否保留、重构或重建，由 Ethan 在看到差异报告后决定。

## 永久禁止的工作方式

- 看一张图就自由发挥整套商城。
- 一次性批量写完所有页面再让 Ethan 验收。
- 为了让代码“更好写”而改变批准设计。
- 用新设计覆盖旧设计，不保留差异说明。
- 在没有真实开发者工具截图的情况下宣布完成。
- 把功能齐全误当成视觉合格。
- 遇到编译错误时怀疑网络，却不先读取本地错误行和 WXSS 报错。

正确方式只有一个：读规范 → 建映射 → 单页实现 → 实机对照 → Ethan 确认 → 下一页。
