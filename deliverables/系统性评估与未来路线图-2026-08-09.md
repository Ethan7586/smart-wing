## 0. 一句话结论

**当前系统是一个"响应式 Web 应用"，不是"多端原生应用"**——小程序、Android App 这些入口目前都是
**同一份 React 网页代码，套了一层对应平台的视觉皮肤**，通过浏览器/webview 访问，不是编译进微信
小程序平台或应用商店的独立产物。这个定位没有错（MVP 阶段完全合理），但如果未来目标是"真正上架
微信小程序""真正上架 App Store/应用宝"，需要的是**新的开发工程**，不是现有代码的配置调整。

并发方面：**硬件够，软件配置不够**，改一个参数（PM2 单进程 → 集群模式）能大幅提升，但 1000 人真并发
最终能不能扛住，还卡在两个我查不到、需要你去确认的数字上（服务器带宽、Supabase 套餐上限）。

## 2. 1000 人并发：具体卡在哪，怎么解决

### 2.1 硬件层——够用

阿里云 ECS 8 核 / 14 GiB 内存，高于文档最低要求，本身不是瓶颈。

### 2.2 软件层——现在不够，但改起来不难

**当前**：`ecosystem.config.cjs` 里 `instances: 1, exec_mode: 'fork'`——不管服务器有几个核，Node 应用
只用其中 1 个核跑。这个应用有服务端渲染（SSR），渲染是 CPU 密集型工作，单进程下大量并发请求会
直接排队，是目前最大的单点瓶颈。

**改法**（等你决定要上量的时候，我可以直接做）：
```js
instances: 'max',        // 或者写具体数字，比如 6（留 2 核给系统和数据库连接池）
exec_mode: 'cluster',
```
PM2 的 cluster 模式会在多个进程间自动做负载均衡，8 核基本可以理解为并发承载能力提升到接近 8 倍
（不是精确线性，但量级上是这个级别）。

### 2.3 两个我查不到、必须你去确认的数字

1. **服务器实际带宽**：阿里云控制台 → ECS 实例详情 → 带宽那一栏。1000 人同时刷页面/图片/接口，
   带宽不够会直接堵死，跟 CPU、代码都没关系。建议至少 20-50Mbps 起步（具体要看页面和图片大小，
   有条件的话上 CDN 分流会更从容）。
2. **Supabase Free Plan 的连接数/请求频率上限**：新建的这个项目是免费版，官方对并发数据库连接数
   和 API 请求速率有硬性上限，1000 人同时下单/查询很可能撞到这个限制。需要去 Supabase 项目的
   Settings/Billing 页面查具体数值，判断要不要升级付费版。

### 2.4 结论

**"1000 人同时在线（挂着不动）"和"1000 人同时发请求（狂点刷新/同时下单）"是两个完全不同的量级**。
前者现在的配置大概率扛得住（大部分时间用户是闲置的，服务器基本没压力）；后者需要先把 2.2 的
PM2 集群模式改掉，并且拿到 2.3 那两个数字确认过后，才能给出真正靠谱的结论。

## 3. 多端能力的真实边界（这是本报告最重要的澄清）

### 3.1 现在有什么

代码里确实有 `src/features/android/`、`src/features/miniprogram/`、`src/features/tablet/` 这些目录，
里面的组件命名也很"像"（`WeChatCapsule`、`WeChatTabBar`、`MPHomePage` 这种），容易让人以为已经做了
真正的多端开发。**实际检查后的结论是**：

- 这些全部是**普通 React 组件**，用 CSS 把界面做成"看起来像微信小程序""看起来像安卓 App"的样子
- 运行方式是：用户用手机浏览器（或者微信内置浏览器）打开一个网页，网页里的 JS 检测设备类型，
  切换渲染成对应的界面皮肤——**本质上还是同一个网站，同一套构建产物**
- `package.json` 里没有任何原生/跨端开发框架（React Native、Capacitor、Taro、uni-app、微信小程序
  SDK 这些都没有）
- 这意味着：它**不能**直接提交到微信小程序后台审核上架，**不能**直接打包提交 App Store 或应用宝

### 3.2 这是不是问题？

**对 MVP 阶段来说不是问题，甚至是对的选择**——响应式网页开发速度快、维护成本低、一套代码多端复用，
适合验证产品逻辑。企业内部福利商城这种场景，员工大概率是通过链接/二维码访问，不一定需要"正式上架"
这个动作。

**但如果未来目标包含以下任意一条，就需要新的工程投入，不是现有代码能直接满足的：**

- 要在微信生态内以"小程序"身份出现（用户在微信"发现-小程序"里能搜到/收藏）
- 要上架 App Store / 应用宝，用户能在应用商店搜到下载
- 需要用到原生能力（推送通知、扫码硬件调用、更流畅的原生交互体验、离线能力）

### 3.3 真要做，三条路径（复杂度递增）

| 路径 | 说明 | 复杂度 | 是否复用现有代码 |
|---|---|---|---|
| **PWA 加强** | 现有网页基础上加 manifest + service worker，支持"添加到主屏幕"、
  离线缓存、推送通知（部分能力） | 低 | 大量复用 |
| **微信小程序（uni-app/Taro 改造）** | 用 uni-app 或 Taro 这类跨端框架把现有 React/业务逻辑
  部分迁移过去，编译出真正的小程序包 | 中高 | 部分复用（UI 层要重写，业务逻辑/API 调用层可以
  大部分保留） |
| **iOS/Android 原生 App** | React Native 或 Flutter 重新做一套客户端，调用现有 `worker/api/*`
  接口（这层是通用的，谁调用都一样） | 高 | 只复用后端 API，前端要重新做 |

**共同的好消息**：不管走哪条路，`worker/api/*` 那一层（下单、支付、库存、账户这些核心业务 API）
都是平台无关的 REST 接口，**这部分完全不用动**，新客户端直接调用现成接口就行。真正要重做的是
"界面和交互层"，不是"业务逻辑层"——这也是当初把业务逻辑收敛到 RPC/Worker 层这个架构决策的价值
所在。

## 4. 优先级建议

如果近期没有"必须上架微信小程序/App Store"这种硬性截止日期，建议顺序：

1. **先把并发这件事的两个未知数字查清楚**（带宽、Supabase 套餐上限），成本几乎为零，只是去后台
   看一眼
2. **PM2 切集群模式**——改动小，随时可以做，不需要等到真有 1000 人的时候才手忙脚乱
3. **数据合规问题拿到明确结论**（境内存储要不要求），这个决定会影响到底要不要放弃 Supabase 自建
   数据库，越早确认越好，因为一旦真到了要迁移数据库的阶段，成本会指数级上升
4. **多端原生化**放在最后——除非有明确的业务时间点（比如甲方要求"必须能在微信小程序里用"），
   否则这是一笔可以往后推的投入，现有响应式方案在验证阶段完全够用
